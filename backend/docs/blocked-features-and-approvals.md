## 2. Blocked Feature: Appointment Booking

### A. Source Evidence
Inspection of `src/modules/appointment/`:
- `src/modules/appointment/presentation/controllers/appointment.controller.ts`:
  ```typescript
  import { Controller } from '@nestjs/common';
  @Controller('appointments')
  export class AppointmentController {}
  ```
- No routes, endpoints, parameters, or decorators exist on this controller.
- Inspection of `prisma/schema.prisma` confirms:
  - There is NO `Appointment` model.
  - There is NO `Consultation` or `BookingSlot` model.
  - There are NO foreign keys linking `PatientProfile` and `DoctorProfile` for scheduled visits.

### B. Mandatory Safety Restriction
Modifying `prisma/schema.prisma`, running migrations, or executing `prisma db push` is strictly prohibited by project constraints. Therefore, appointment booking cannot be implemented safely in code without introducing unbacked routes or schema changes.

### C. Proposed Architecture (For Future Approval)
To unblock this feature in a future approved phase:
1. **Schema Migration:** Add `model Appointment` with fields:
   - `id` (UUID), `patientProfileId` (FK -> `PatientProfile`), `doctorProfileId` (FK -> `DoctorProfile`)
   - `status` (`SCHEDULED`, `CONFIRMED`, `CANCELLED`, `COMPLETED`)
   - `scheduledAt` (DateTime), `durationMinutes` (Int), `meetingUrl` (String optional), `notes` (String optional)
2. **DTO & Validation:** Implement `CreateAppointmentDto`, `RescheduleAppointmentDto`, and `CancelAppointmentDto`.
3. **Double-Booking Prevention:** Implement transactional locking (`SELECT FOR UPDATE` or Prisma serializable transactions) to prevent concurrent double-booking of doctor availability slots.

## 3. Blocked Feature: Doctor Access to Patient Clinical Records

### A. Current Source Behavior
- In `src/modules/medical-record/application/use-cases/medical-record.service.ts` (lines 130–136):
  ```typescript
  const record = await this.medicalRecordRepository.findById(id);
  if (!record) throw new NotFoundException('Medical record not found');
  if (record.patientProfileId !== callerProfileId) {
    throw new ForbiddenException('You do not have access to this record');
  }
  ```
- A doctor authenticates with role `DOCTOR` and possesses a `doctorProfileId`.
- When a doctor attempts `GET /api/v1/medical-records/:id`, `record.patientProfileId !== callerProfileId` evaluates to `true`, and the application correctly throws **HTTP 403 Forbidden**.
- In `src/modules/qr-code/`, `QrCodeService.verifyPatientQr` verifies that a QR payload was generated by a patient, but **DOES NOT** grant any authorization to query the `medical-records` or `reports` tables.

### B. Why This Cannot Be Weakened
Weakening the ownership check to `if (user.role === 'DOCTOR') return record;` would create a critical security vulnerability allowing any doctor on the platform to read every patient's private medical history and lab reports without authorization.

## 4. Technical Proposal: Patient-Consent Token Flow (RFC)

To securely enable doctors to view patient records during a consultation, the following cryptographically signed consent token workflow is proposed:

```
+---------------+                +---------------+               +---------------+
| Patient App   |                | Doctor App    |               | CareID Backend|
+---------------+                +---------------+               +---------------+
       |                                |                                |
       | 1. Patient taps "Grant Access" |                                |
       |    selects Doctor & Duration   |                                |
       |---------------------------------------------------------------->|
       |                                |   2. Signs Consent Token JWT   |
       |                                |      (15-min expiry, specific  |
       |                                |       doctor & patient IDs)    |
       |<----------------------------------------------------------------|
       | 3. Displays dynamic QR or sends                                 |
       |    Consent Token to Doctor     |                                |
       |------------------------------->|                                |
       |                                | 4. Doctor requests record      |
       |                                |    with Consent Token header   |
       |                                |------------------------------->|
       |                                |                                | 5. Verifies:
       |                                |                                |    - JWT signature
       |                                |                                |    - Not expired (<15m)
       |                                |                                |    - Token.doctorId == Req.doctorId
       |                                |                                |    - Token.patientId == Record.patientId
       |                                |                                |    - Nonce not revoked
       |                                |                                |    - Logs AuditEvent
       |                                |<-------------------------------|
       |                                | 6. Returns Clinical Record     |
```

### Protocol Specifications:
1. **Issuer & Authorization:** Only the authenticated patient (`PATIENT` role) can request issuance of a Consent Token from `/api/v1/clinical/consent/grant`.
2. **Cryptographic Binding:**
   The consent token payload is a signed JWT containing:
   ```json
   {
     "sub": "patient-profile-uuid",
     "aud": "careid-clinical-access",
     "doc": "doctor-profile-uuid",
     "scope": ["medical_records:read", "reports:read"],
     "jti": "unique-consent-uuid",
     "iat": 1729900000,
     "exp": 1729900900
   }
   ```
3. **Strict Time-to-Live (TTL):** Maximum validity of 15 minutes (`exp = iat + 900`).
4. **Replay & Revocation:**
   - Single-session or revocable token: Stored in a lightweight `active_consents` table or invalidated on demand.
   - Patient can tap "Revoke Now" in the patient app to immediately terminate the doctor's access window.
5. **Auditing:** Every read performed using a Consent Token emits a tamper-evident record in `audit_events` recording:
   - Doctor ID, Patient ID, Consent Token JTI, Record ID, Timestamp, and Doctor IP address.
6. **Failure Mode:** Any token signature failure, expired token, mismatch in doctor ID, or revoked JTI results in immediate **HTTP 403 Forbidden**.

## 5. External Infrastructure Dependencies

| Dependency | Purpose | Impact of Absence | Remediation Path |
| :--- | :--- | :--- | :--- |
| **Redis / Valkey** | Distributed rate limiting across PM2 workers & token revocation cache. | Process-local rate limiter allows up to 4x configured requests across PM2 cluster. | Provision Redis container; configure `REDIS_URL` in `.env.production`. |
| **ClamAV / Malware Scanner** | Antivirus scanning of uploaded PDFs and medical images. | Files remain marked as `virusScanStatus: 'PENDING'`. | Deploy `clamd` on host or integrate AWS GuardDuty S3 malware scan. |
| **Object Storage (S3 / R2 / GCS)** | Scalable, redundant medical file storage with presigned URLs. | Files stored on local VPS filesystem (`/uploads`), risking disk exhaustion. | Provision S3-compatible bucket and configure presigned URL generator. |
| **Production SMS Gateway** | Delivery of real-time 6-digit OTP codes to patient and doctor phones. | Staging OTPs or mock delivery required if SMS provider is unavailable. | Configure verified Brevo/Twilio API keys in production environment. |
