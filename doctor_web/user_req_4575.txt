# CAREID — ADMIN DOCTOR REGISTRATION TO DOCTOR EMAIL/PASSWORD LOGIN
## Complete End-to-End Account Provisioning Integration

### Objective

Implement a complete workflow in which an Administrator registers a Doctor through the Admin Portal, the system creates the Doctor's actual login account with a temporary password, and that Doctor can log in through the Doctor Web portal using the registered email and temporary password.

After successful authentication, the Doctor must land on their own Doctor Dashboard with their correct Doctor Master Registry profile.

This must be a real backend-integrated workflow, not a frontend simulation.

## 2. Admin Doctor Registration Workflow

Existing Admin route:

`/admin/doctors/create`

When an Administrator registers a Doctor, the system must:

1. Create the Doctor's clinical profile.
2. Create an associated authentication user account.
3. Associate the authentication account with the correct Doctor profile.
4. Assign the correct `DOCTOR` role.
5. Associate the Doctor with the selected primary facility.
6. Preserve medical license and verification document information.
7. Generate a secure temporary password.
8. Return the generated temporary password to the authorized Admin only once, if supported by the backend security design.

The account must be created as part of one logically consistent registration workflow.

Do not create a Doctor profile without a linked login account and then incorrectly report that registration is complete.

If account provisioning fails, clearly report the failure and avoid creating orphaned or duplicate Doctor records.

Use database transactions or an existing safe orchestration mechanism where appropriate.

---

## 3. Temporary Password Requirements

The temporary password must:

- Be generated securely on the backend.
- Meet the existing password policy.
- Never be hardcoded.
- Never be stored in plaintext.
- Be hashed using the backend's existing secure password hashing mechanism.
- Never appear in application logs.
- Never be exposed in API responses after the initial authorized provisioning response.
- Be accessible only to the authorized Administrator during account provisioning.

If the backend supports forced password change, require the Doctor to change the temporary password after first successful login.

Do not implement a fake first-login password-change mechanism without backend support.

Inspect the existing implementation and integrate it with the real backend authentication workflow.

Expected request:

Use the actual authentication endpoint and DTO defined by the backend/Postman collection.

The frontend must:

1. Submit the Doctor's email and password.
2. Receive the actual backend authentication response.
3. Store authentication tokens using the existing secure authentication architecture.
4. Validate the authenticated user.
5. Verify that the account has the `DOCTOR` role.

## 5. Identity and Profile Linking

This is a critical requirement.

Verify the relationship:

`Authentication User ID → Doctor Profile ID → Primary Facility ID`

Ensure:

- The registered email belongs to the created authentication user.
- The authentication user has the DOCTOR role.
- The Doctor profile is linked to that exact user ID.
- The Doctor's primary facility assignment is correctly persisted.
- `GET /api/v1/auth/me` returns the correct authenticated identity.
- `GET /api/v1/doctors/me` returns the corresponding Doctor profile.

Prevent a login from loading another Doctor's profile.

Do not rely on frontend static IDs, hardcoded Doctor data or local storage identity overrides.
